# ADR-001: Формат доказательств Tendermint 0.34.19

Статус: принято. Дата: 13 ноября 2026 года; дополнено 14 ноября.

## Контекст

Эталон — `third_party/tendermint` из Minter Go `a3aac90a4f7995fccaf3cd4e4c34c89ff0c7544c`, форк 0.34.19. Проверки ниже относятся к этой закреплённой версии.

Типы tendermint-rs 0.40.4 вводят ограничения, которых нет на пути Go 0.34.19 `EvidenceFromProto → ValidateBasic → VerifyLightClientAttack`. В частности, это касается порядка валидаторов, соответствия адреса ключу, коротких подписей в пропускаемых позициях и типов ключей. Они также могут отбросить raw-поля до проверки. Подстановка этих типов изменяла результат приёма доказательства и возможность декодировать содержащий его блок.

В Go полная проверка обычного commit и light-проверка используют разные правила. `VerifyCommitLight` и `VerifyCommitLightTrusting` пропускают Nil/Absent и возвращаются сразу после нужного веса. `GetByzantineValidators` и `ABCI` выполняют разные преобразования адреса: выбор списка использует wire-адрес, а `TM2PB.Validator` выводит адрес из публичного ключа.

## Решение

Проверять protobuf доказательства по правилам закреплённого Go в `minter-p2p::evidence`. Сохранять порядок массива валидаторов и проверять структуру до преобразований. Криптографическую проверку выполнять только для подписей, которые проверяет соответствующая функция Go. Использовать совместимый Ed25519 и существующий k256 для secp256k1; адрес secp256k1 вычислять через RIPEMD160(SHA256(key)).

`ReceivedBlock` предоставляет `NativeBlock`: типизированные заголовок и последний commit, транзакции и список protobuf-доказательств. Хеши и PartSet строятся из представления, соответствующего Go `ToProto`. Пустой начальный commit сохраняет прежнее внутреннее представление `None`. Для ABCI используется тот же канонический заголовок.

Отдельно хранится размер входного Go protobuf списка доказательств. Go `EvidenceData.byteSize` сохраняет `EvidenceList.Size()` до семантической канонизации; удаление cached total или приведение флага к byte могут уменьшить размер. `Evidence.MaxBytes` проверяется по исходному размеру с восстановлением Go nonnullable-полей. Его нельзя заменять размером канонического списка.

Полная проверка подписей обычных блоков остаётся в `verify::verify_commit`.

Для восстановления PartSet `ReceivedBlock` сохраняет канонические байты блока, по которым вычислен его ID. `BlockParts::from_block` использует этот буфер. Повторная сериализация исходного ответа могла давать другой PartSet для преобразуемых полей, хотя декодирование уже прошло. Исходные байты ответа и исходный размер evidence сохраняются независимо. Цена — дополнительный буфер размером с канонический блок для каждого удерживаемого `ReceivedBlock`; повторный разбор и сериализация при построении частей больше не нужны.

## Проверка и последствия

Детерминированный Go-корпус включает 39 положительных и отрицательных входов. Rust сравнивает результат проверки, декодирование `BlockResponse`, EvidenceHash, BlockHash, PartSetHash, protobuf заголовка для ABCI, входной размер и байты ABCI evidence. Все декодируемые блоки повторно разбиваются на части и собираются в обратном порядке. Размер и число частей сверяются с Go, включая блок из двух частей. Генератор запускается в закреплённом Go-модуле; все ключи тестовые и выводятся из опубликованных констант.

Проверки покрывают конкретный корпус; они не доказывают полноту всех возможных входов. Для готовности валидатора остаются более широкая проверка консенсуса и контекст до снимка. При смене версии эталона повторно проверить контракт и обновить корпус.
