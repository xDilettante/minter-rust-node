# Перевыпуск монет и токенов

## Задача и область

Перенести два оставшихся активных типа: `RecreateCoin` (0x10) и `RecreateToken` (0x1f). Совпадение с закреплённым Go означает полные ответы ABCI, порядок проверок, комиссии, текущую и прежние версии тикера, баланс и AppHash. В этом этапе синтетический корпус дополняет историческую сверку; он не объявляет все исторические правила закрытыми.

Карта возможностей: (1) декодирование/проверки, (2) комиссии и баланс, (3) смена версии/регистрация нового ID, (4) видимость изменений внутри блока, (5) сохранение/импорт/повторное открытие, (6) сверка с Go на обеих ОС. Публичные API и бинарный формат дерева не расширяются. Зависимости и хранилище остаются прежними.

## Контракт Go

- Поля RLP совпадают с CreateCoin/CreateToken. Цена берётся из отдельных `recreate_coin`/`recreate_token`; gas=5 до общих надбавок. Дополнительная цена тикера и его сжигание не применяются.
- Имя проверяется первым. У токена затем проверяются неизменяемая эмиссия, границы InitialAmount и MaxSupply. У резервной монеты порядок: InitialAmount, MaxSupply, InitialReserve, CRR. Затем ищется текущая версия и проверяется владелец символа. Проверки нового имени символа и отказа существующему символу из Create не переносятся.
- Проверки gas/баланса идут после basicCheck. У RecreateCoin: gas отдельно → начальный резерв отдельно → сумма gas+резерв при BIP gas. Ошибки повторяют Go, включая Info и порядок полей.
- Прежняя текущая модель получает `max(version по всей истории)+1` в uint16, включая поведение переполнения Go. Новый ID имеет версию 0. Список ID символа дополняется, прежние объёмы, резервы, балансы, пулы и стейки остаются доступны по старым ID. Переход резервной монеты в токен и обратно допускается Go.
- Владелец принадлежит символу и сохраняется при перевыпуске. Повторный перевыпуск, изменение владельца, mint/burn и gas старой монетой в одном блоке должны видеть актуальные модели. Дополнительная плата gas не должна теряться при смене версии старой модели.
- Теги после смены версии включают текущий символ/новый ID и полный символ прежней монеты с её новой версией/старый ID; старый ID индексируется, старый символ не индексируется.
- Запись повторяет порядок Go по убыванию dirty ID: история символа только для созданного ID, модель при её изменении, supply только при изменении, owner при его изменении. Изменение version не создаёт лишнюю запись supply. Общая информация владельца не должна откатываться устаревшей копией при нескольких операциях.

Источники: локальный Go `a3aac90a4f7995fccaf3cd4e4c34c89ff0c7544c`, `coreV2/transaction/recreate_{coin,token}.go`, `coreV2/state/coins/{coins,model}.go`, decoder и таблица gas. Базовые типы и расчёт комиссии переиспользуются; история моделей проверяется по реальным ключам IAVL.

## Реализация

Существующий `Creation` переиспользуется как разобранные поля. Новые варианты Data и план операции отделяют перевыпуск от создания тикера. Изменения моделей и полной истории символа учитываются существующими `coins::Changes`/`View`; сначала собирается Go-корпус, затем фиксируется точный минимальный набор изменяемых полей. Формат RLP моделей, layout RocksDB и API v2 уже содержат version и остаются прежними.

Нужные файлы: `transaction/coin.rs`, `transaction.rs`, `coins.rs`, `lib.rs`; отдельный Go-генератор и Rust-тест корпуса. Никакой новой БД, службы или адаптера.

## Проверка

1. Подготовить детерминированный Go-корпус из открытых тестовых ключей. Проверять код каждой доставки при генерации. Сохранить snapshot/manifest, полные ABCI, physical coin keys и события.
2. Получить RED на неподдерживаемом типе до изменения production Rust.
3. Сверить положительные/отрицательные проверки и их приоритет; существующие исторические версии; повторный перевыпуск и смену владельца в одном блоке; оба направления coin/token; mint старой версии; gas в BIP, резервной монете и пуле, включая именно перевыпускаемую монету; нехватку резерва отдельно от комиссии; CheckTx активного ExecutorV3 с изолированным mempool и minGasPrice=1, включая нулевую и отличную от BIP цену; uint16-границу. Это отдельные executor-пробы, без заявления о запуске Go-мемпула.
4. После каждого блока сравнить все ABCI и IAVL с Go, открыть Rust заново, экспортировать/импортировать физический снимок. Отдельно проверить непрерывное состояние Go и состояние после его холодного импорта там, где кэш может влиять на порядок записи.
5. На Windows 11 и Ubuntu 24.04 проверить остановки до/после Commit и доказательства сохранённых моделей. Выполнить применимые workspace-тесты, Clippy, release; сохранить происхождение источников, входов и запускаемых бинарников.

Порядок работ: корпус и RED → декодирование/проверки/комиссии → модели и применение → оба направления и пограничные сценарии → обе ОС и архив. Реестр задач — существующие `outputs/tasks/todo.md` и `plan.md`. При расхождении не упрощать ожидаемый Go-результат, а найти первую отличающуюся операцию.
