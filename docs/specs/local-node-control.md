# Управление десктопной нодой из другого процесса

## Цель и границы

GUI и `minterctl node` одного пользователя управляют нодой, уже запущенной другим экземпляром общего контроллера для той же папки данных. Поддерживаются full и light, включая начальное восстановление и текущую одноразовую light-команду. Внешний процесс без этого контроллера остаётся доступен только для наблюдения через прежний API. Здесь не добавляются системная служба, удалённое управление или смена пользователя процесса.

`minterctl node stop --config FILE` запрашивает штатную остановку и дожидается закрытия дочернего процесса и освобождения блокировок. GUI показывает возможность управления, различая владение процессом и возможность отправить локальную команду. Перезапуск из GUI после CLI означает передачу управления новому контроллеру. Cleanup владельца использует отдельный `stop_owned` без внешнего fallback, даже если его Active уже завершён/собран. Завершающийся прежний CLI не останавливает заменившую его ноду.

## Доступ и идентичность

- Транспорт не использует TCP/HTTP: Unix domain socket в приватном каталоге пользователя и Windows named pipe с protected DACL только для SID текущего пользователя. Remote pipe clients отклоняются.
- Клиент и сервер проверяют пользователя собеседника. Unix использует peer credentials. Windows клиент проверяет SID процесса сервера и ограничивает impersonation при открытии pipe.
- Адрес определяется по идентичности существующей папки данных: device/inode в Linux; volume serial/file index в Windows. Это поддерживает symlink, пробелы, Unicode и алиасы регистра Windows, избегая длинного Unix socket path. Сокет живёт в коротком каталоге с владельцем UID и правами 0700, сам сокет — 0600. Небезопасный существующий каталог или посторонний файл не изменяется.
- Сервер создаётся только после получения обеих существующих блокировок конфигурации и папки данных, до запуска дочернего процесса. Устаревший Unix-сокет удаляется только в этой защищённой папке при удержании блокировки данных. Windows использует first-pipe-instance при первом создании.
- Локальные процессы того же пользователя и администратор ОС находятся вне границы изоляции. Права не передаются другим пользователям, настройки/ключи через канал не отправляются.

## Протокол и состояние

Один запрос на соединение: JSON версии 1 с командами `status` или `stop` и ожидаемым full/light режимом. Каждый запуск имеет случайный 128-битный instance ID. `status` возвращает его, `stop` требует точного ID наблюдавшегося владельца; несовпадение не меняет флаг остановки. Свежий CLI сначала узнаёт ID, GUI использует последний показанный. Повтор соединения после ошибки не перенаправляет stop новому владельцу. Перед JSON — длина u32 big endian. Максимум запроса 1 КиБ, ответа 64 КиБ; неизвестные поля, команды, версии и другой режим отвергаются без остановки ноды. Чтение запроса и запись ответа ограничены по времени. Клиент ждёт EOF после ответа; это позволяет дождаться закрытия старого pipe перед следующим запуском. Сервер последовательно обрабатывает ограниченные запросы, не создавая неограниченного числа задач.

Статус расширяется полями `controllable` и необязательным `controlId`: true/ID для собственного активного контроллера или подтверждённого локального сервера. `managed` сохраняет прежний смысл владения в текущем процессе. Внешний работающий контроллер получает фазу attached с возможностью остановки; начальный запуск сохраняет фазу starting. Источник статуса — настройки владельца, поэтому чужой процесс не открывает живую redb/RocksDB для записи. Терминальная ошибка собственного worker не заменяется HTTP-ответом другого процесса на том же порту. Подтверждённый новый IPC-владелец остаётся доступен, а ошибка прошлого собственного запуска возвращается отдельно как `previousError`, не уничтожая результат для owner cleanup.

Если IPC отсутствует, чтение сохранённого light-заголовка удерживает data lease до завершения `light status`, поскольку этот вызов открывает redb эксклюзивно. Занятая lease исключает чтение: наблюдатель сообщает о занятой папке без второго открытия базы.

Общий контроллер обрабатывает собственную и внешнюю остановку одним watch-флагом. Worker завершается и база закрывается, listener закрывается и его Unix pathname удаляется, удаляющий guard уничтожается, результат фиксируется в памяти и журнале, обе блокировки освобождаются; затем отправляется результат ожидающему stop-клиенту. Никакое отложенное удаление не может задеть адрес нового владельца. Ошибка worker возвращается вызывающему процессу. Ответ не означает простой приём команды. Потеря stop-клиента не отменяет уже полученный запрос. Протокольные ошибки клиентов не завершают ноду. Отсутствие IPC не считается подтверждённой остановкой внешнего worker: клиент возвращает понятную ошибку, а не объявляет его завершённым. Повторная собственная остановка остаётся допустимой.

Управляющий клиент ограничивает status восемью, stop — пятьюдесятью секундами; существующий 40-секундный аварийный предел дочернего процесса сохраняется. При невозможности подтвердить остановку возвращается ошибка. Недоступный канал не даёт права посылать сигналы по PID или открывать вторую базу для записи.

Выход из tray при терминальной ошибке показывает окно и сообщение, не закрывая приложение молча. Явный выход из интерфейса может подтвердить уже показанную ошибку после закрытия собственного worker; неподтверждённая остановка остаётся ошибкой. Простое закрытие окна продолжает прятать GUI в tray.

## Изменения и проверка

Собственный full-контроллер обращается к HTTP-статусу только после строки готовности в stdout своего `minterd`, выпущенной после подготовки состояния и bind HTTP/P2P. Из неё сохраняется публичный node ID; последующий API должен вернуть тот же `node_id`. Для распознавания хранится не более 128 байт префикса строки, журнал продолжает получать исходные байты. Ответ HTTP ограничен 64 КиБ независимо от Content-Length. После запроса повторно проверяются исходное поколение и состояние worker: запоздалый ответ не скрывает завершение. Без собственного worker standalone API остаётся доступен только для наблюдения, в том числе после остановки прежнего локального владельца. Несоответствие ID или неверный ответ показывает ошибку API при сохранённой возможности остановки контроллера.

Реализация — `crates/minter-node-control` (общий наблюдатель статуса и приватный IPC с двумя платформенными транспортами), `src/bin/minterctl/node.rs` (stop), GUI `desktop/src` (controllable). Используются Tokio и уже закреплённые platform SDK; формат БД и параметры консенсуса не меняются.

Команды: `cargo test -p minter-node-control --locked`; `cargo test --workspace --locked`; `cargo clippy --workspace --all-targets --locked -- -D warnings`; `cargo build --workspace --release --bin minterd --bin minterctl --locked`. GUI сохраняет собственные npm check/build и production WebView проверки.

Приёмка:

1. На Windows и Linux разные экземпляры контроллера читают статус и останавливают full/light; чужой режим, протокол и чрезмерные/оборванные сообщения не останавливают узел. Остановка не создаёт отсутствующую папку данных.
2. Проверены права канала и пользователь собеседника; путь-алиас на ту же папку находит тот же сервер. Посторонние файловые записи не удаляются. Устаревший сокет восстанавливается после закрытия владельца, второй живой контроллер не вытесняет первый.
3. Полная нода проверяется с настоящими Go-пирами и AppHash после остановки/повторного запуска. Отдельно — отмена реального снимка до готового head и последующее восстановление. Лёгкая нода проверяется во время незавершённого запроса и после ошибки, с ожиданием закрытия redb.
4. В GUI настоящим WebView: CLI → наблюдение/остановка/запуск GUI; GUI → status/stop CLI; повторная передача управления не оставляет дочерние процессы и не завершает новую ноду из старого CLI.
5. CLI-сценарии исполняются на Windows 11 и нативной Ubuntu 24.04, GUI Ubuntu/WSL2 отмечается отдельно от чистой графической системы. Установщики и службы остаются отдельной приёмкой.
